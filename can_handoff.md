# WSL / SocketCAN / 2024 Mazda MX-5 ND Setup

## Objective and Results

This document summarizes a validated configuration for using a CANable adapter
from Ubuntu on WSL2 to communicate with a 2024 Mazda MX-5 ND OBD-II port. It was
prepared as starting context for a project in another workspace.

Confirmed results:

- The custom kernel boots in WSL.
- SocketCAN modules load and a virtual `vcan` interface works.
- The CANable is recognized by `gs_usb` and exposes `can0`.
- An OBD-II engine RPM request received a response at 500 kbit/s.
- The response indicates approximately 721 RPM, consistent with idle.

## Kernel and Deployed Files

The working configuration is `.config-can-wsl`, derived from
`Microsoft/config-wsl`. The following options are enabled as modules:

```text
CONFIG_CAN=m
CONFIG_CAN_RAW=m
CONFIG_CAN_BCM=m
CONFIG_CAN_VCAN=m
CONFIG_CAN_SLCAN=m
CONFIG_CAN_GS_USB=m
CONFIG_CAN_PEAK_USB=m
CONFIG_CAN_KVASER_USB=m
CONFIG_USBIP_VHCI_HCD=m
```

Other CAN modules were also built, including ISO-TP, J1939, and several other
USB drivers. Building them does not constitute a hardware test.

A build with 12 jobs was followed by a WSL crash. Memory pressure is a likely
but unproven cause. WSL had 3.5 GiB RAM and 1 GiB swap at the time. The
successful build used `-j1` and:

```text
CONFIG_DEBUG_INFO_NONE=y
# CONFIG_DEBUG_INFO_BTF is not set
```

To retain this choice, `DEBUG_INFO_DWARF_TOOLCHAIN_DEFAULT` had to be disabled,
then `DEBUG_INFO_NONE` enabled before `olddefconfig`. Do not copy a
configuration over the existing one without checking local modifications.

Build commands used from the repository root:

```bash
make KCONFIG_CONFIG=.config-can-wsl olddefconfig
make KCONFIG_CONFIG=.config-can-wsl -j1 > .wsl-kernel-build.log 2>&1
make KCONFIG_CONFIG=.config-can-wsl modules_install INSTALL_MOD_PATH="$PWD/modules"
make KCONFIG_CONFIG=.config-can-wsl headers_install INSTALL_HDR_PATH="$PWD/headers"
make -C tools/perf -j1 NO_JEVENTS=1 NO_JVMTI=1 NO_LIBTRACEEVENT=1 install DESTDIR="$PWD/perf" prefix=/
```

Useful artifacts in the repository:

- `arch/x86/boot/bzImage`: kernel image, approximately 14 MiB.
- `modules/lib/modules/6.18.58.1-microsoft-standard-WSL2+/`: installed modules.
- `modules-can-wsl259.vhdx`: corrected module disk currently in use.
- `headers/` and `perf/`: additional exports, not needed to open a CAN socket.
- `.wsl-kernel-build.log`: persistent build log.
- `.wsl-tools/`: locally extracted packaging tools and intermediate image.

Missing packaging tools were downloaded without system installation using
`apt-get download`, then extracted with `dpkg-deb -x`: `qemu-utils`,
`libnuma1`, `liburing2`, and `libaio1t64`. `mke2fs` and `debugfs` were available.

### Critical Point: VHDX Format for WSL 2.5.9

The `Microsoft/scripts/gen_artifacts_vhdx.sh` script from this checkout created
an `<release>/modules/...` tree. On this machine, WSL 2.5.9 mounts the VHDX root
directly under `/lib/modules/<release>`; the nested format therefore prevented
`modprobe` from finding the modules.

The corrected VHDX contains directly at its root:

```text
/
  kernel/
    net/can/can.ko
    net/can/can-raw.ko
    drivers/net/can/vcan.ko
    drivers/net/can/usb/gs_usb.ko
    ...
  modules.dep
  modules.dep.bin
  modules.alias
  modules.alias.bin
  modules.builtin
  ...
```

It was generated by copying the contents of the installed module directory to
a staging directory, without the `build` and `source` links, then using
`mke2fs -d` and `qemu-img convert -f raw -O vhdx`. `debugfs` confirmed the
internal paths, `qemu-img compare` confirmed the converted contents, and
SHA-256 hashes confirmed the Windows copy. This format is validated on WSL
2.5.9; verify it again if the WSL version changes.

**Do not reuse the old `modules-can.vhdx` on this machine.**

## Attaching USB from Windows to WSL

PowerShell can be accessed from WSL with `powershell.exe -NoProfile`.

In Windows PowerShell:

```powershell
usbipd list
# Once, as administrator if the device has not yet been shared:
usbipd bind --busid 1-1
# One-time attachment:
usbipd attach --wsl --busid 1-1
# Or automatically follow disconnects/reconnects:
usbipd attach --wsl --hardware-id 1d50:606f --auto-attach
```

The `--auto-attach` watcher was started and reconnection after unplugging was
observed. It depends on a process that must remain active; no scheduled Windows
task or startup service was configured. Do not start multiple concurrent
watchers for the same adapter. Attachment temporarily removes the device from
Windows applications.

After each reconnection, `can0` may return in the `DOWN` state without a
configured bitrate: USB attachment and bus configuration are separate steps.
If the CANable is absent from the `Connected` section of `usbipd list`, first
check the USB connection, data cable, and power.

```bash
uname -r

```

Loading modules and configuring interfaces require privileges. Do not collect
passwords in the project or an agent. Captures worked without `sudo`. `candump`
and `cansend` are available on this machine; on another distribution, install
`can-utils` if necessary.

## Passive Vehicle Listening

Recommended OBD-II wiring to verify on the actual cable: pin 6 CAN-H, pin 14
CAN-L, and pin 5 signal ground. Never apply the 12 V from pin 16 to a CAN or USB
input. Do not add termination to the vehicle bus; check any CANable termination
jumper.

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 listen-only on
sudo ip link set can0 up
timeout 15s candump -t a -e can0
```

Several passive captures, including one with the engine running, received zero
frames. A response to an OBD request was later received: lack of passive traffic
did not therefore mean the bitrate or wiring was incorrect during that
successful test. The exact role of the vehicle gateway was not established.

## Successful Active OBD-II Test

Perform vehicle tests while stationary, in a well-ventilated area. The only
transmission authorized and tested during this session was a standard read
request, not an actuator command or ECU modification.

Enable normal mode, which is required to transmit:

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 listen-only off
sudo ip link set can0 up
```

Start reception in one terminal:

```bash
timeout 15s candump -t a 'can0,7E8:7F8'
```

Then send a single request in another terminal:

```bash
cansend can0 7DF#02010C0000000000
```

This is a functional OBD-II request: service `01`, PID `0C` (engine RPM),
single-frame ISO-TP transport. Response supplied by the user:

```text
(1794346475.712557) can0 7E8 [8] 04 41 0C 0B 45 00 00 00
```

- `7E8`: OBD response identifier.
- `04`: ISO-TP payload length, four bytes.
- `41 0C`: positive response to the engine RPM read.
- `0B 45`: `(0x0B * 256 + 0x45) / 4 = 721.25 RPM`.
- The `timeout` exit code `124` only indicates that the timeout expired.

Recommended return to passive listening after the test:

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 listen-only on
sudo ip link set can0 up
```

This return was recommended, but its execution after the last test was not
confirmed. Always check `ip -details link show can0` at the start of a project.

## Starting Points for the Future Project

- Backend: Linux SocketCAN, `can0` interface, classic CAN at 500 kbit/s.
- Recommended default mode: passive; require explicit action to transmit.
- Check the interface, mode, and errors before each session.
- Handle USB disconnects and interface recreation.
- For Python, consider `python-can`; for multi-frame ISO-TP, reuse an existing
  implementation rather than a custom transport. No application Python
  dependency was installed or validated during this session.
- Only one RPM PID read was validated. Other PIDs, CAN FD, proprietary Mazda
  identifiers, DBC files, and UDS services were not tested.
- Do not scan identifiers, issue actuator commands, clear faults, or program
  ECUs by default.
- Keep captures local: they may contain vehicle information.
- Do not inspect `/proc` process files: an explicit user constraint during this
  session.
